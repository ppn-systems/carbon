## Executive summary

1. **About 4,900 lines of production code have no product caller.**
   - **Graphics:** about 4,300 lines, with tests. Most of `graphics/` is a general-purpose framework: UI controls, focus, layout, screen transitions, scene objects, an asset manager and render targets. The desktop client never uses any of it. It uses only nine-slice drawing, image decoders, `Direction8`, `GameScene` and `SceneManager` (DEAD-1).
   - **Engine:** a further 760 lines are types that only their own unit tests use (DEAD-2).
   - **Both are deleted in this round** (#162, #163).
2. **The same rule is often written twice, and some pairs already disagree.**
   - Build reach: the server allows 3.5 tiles, but `structures.json` says 12 (DUP-1).
   - Forge station: the client looks 6 tiles out, the server 5 (DUP-3).
   - Auto-pickup radius: 32 px vs 36 px (DUP-8).
   - Kill loot lifetime: the code says 120 s at 30 Hz, `economy.json` says 180 s (MAGIC-1).
   - Client move-speed and mana prediction ignore progression stats (DUP-4, **still open SA-3**).
   - Seven more pairs agree today only by coincidence.
3. **New features mostly landed in their own types.** Stamina, status levels, the trade basket and repair each have a service. On the client, death, water, trade and repair have their own sessions and controllers. The exceptions are server water and death, written as `AuthoritativeWorld` partials, and client stamina prediction, written as a `MultiplayerSession` partial. `MultiplayerSession` keeps growing: 4,175 → 4,297 lines and 129 fields. One state lifetime is reset by hand in three places, with 64, 55 and about 30 field writes (SRP-7).
4. **The layer graph is clean** (0 violations). The allocation guard runs against a null outbound sink, so it never measures the real per-send `Task` (ALLOC-1, **still open PERF-3**). It also never measures the per-pulse persistence snapshot that status effects added (ALLOC-2).
5. **The agent docs point at things that do not exist.** These include `analyzer/` and `wasm/` (both empty), `docs/execution/`, and several paths and types in the skills. Seven ADRs are marked **Proposed** although master implements them (DOC-1…11).

## How to read this

- IDs: `DEAD` (code), `DATA` (config, i18n, art, knobs), `DUP` (one rule written twice), `SRP` (responsibility), `LAY`, `ALLOC`, `STATIC`, `MAGIC` (AGENTS.md rules), `DOC` (naming and stale docs).
- **Real drift** means the copies already give different numbers. **Latent** means they agree today but nothing keeps them in step.
- **Conflict** is how likely a change is to collide with in-flight work: **none**, **low**, or **in-flight** (the file is owned by an open PR).
- #162, #163 and #165 are the refactor PRs that ship with this round (see [Phase 2](#phase-2-refactor-prs)). #162 is merged.

**Flaky guard, not reproducible (2026-11-27).** `DeltaColumnPoolTests.RentPopulateReturn_SteadyStateAoi_AllocatesNothing`
failed once inside `verify.sh` while other `dotnet test` processes loaded the CPU (quiet log, so no byte count). Ruled out:
- **Shared state:** each test owns its `DeltaColumnPool`, the pool has no static state, and `DeltaColumns.Empty` is immutable
  and never pooled.
- **Load:** 36 runs of the class with 3 processes at a time plus 4 CPU hogs, and 12 full Host-suite runs (452 tests,
  classes in parallel) plus CPU hogs, never failed.
- **Runtime work in the measured loop:** a cold, single, once-per-process copy of the measurement read 0 bytes in 96
  processes (6 at a time on 4 cores), with and without an in-process thread forcing gen-0 GCs. It also read 0 with each
  of these forced: call-counting delay 0, call-count thresholds 200/600/2000, a background worker timeout of 0, OSR
  after 100 iterations, and TieredPGO off.

The assertion now reports the bytes, the gen-0/1/2 collections and the elapsed time of the measured window, so the next
failure carries its own evidence. `verify.sh` and CI print it; a `-v quiet` run hides every assertion message, so rerun
a failure without it.

A second zero-allocation test, `MenuBackdropTests.ClockFrame_AllocatesNothing` (desktop), then failed once in a quiet
`verify.sh` run with no external load. That makes this one systemic finding about how the tests measure, not about
either piece of code. Every zero-allocation assertion now goes through one shared probe, `tests/Shared/AllocationProbe.cs`,
which `tests/Directory.Build.props` links into every test project:
- **Warm-up:** the body runs first (most sites had 0 to 64 warm-up calls for a 1,000- to 10,000-call window).
- **Measuring loop:** the probe's own loop is compiled fully optimized, so it is never tiered up or replaced on the
  stack mid-window.
- **Two windows:** both are measured, and the assertion stays strict on the first.
- **Report:** bytes, the repeat window, the iterations, elapsed time, GC gen0/1/2 deltas, JIT compilations on the
  thread and the thread id.

One-shot sites use `Start()`/`Stop()` with the same report. What the move showed:
- **JIT inside the window:** a copy of the old `ClockFrame` measurement JIT-compiled one method on the test thread
  inside every one of 40 fresh-process windows. That was the loop's on-stack replacement, so the window was not steady
  state. It still measured 0 bytes there, and the failure did not reproduce.
- **The tick is not steady:** the server tick guards pass on their first 900-tick window (1.2 and 0.0 B/tick), but an
  identical second window allocates 55–59 KB (about 61–65 B/tick). That is real work in a later window, which the guard's
  budget note attributes to monster respawn (ECS-3). It is not runtime noise, and it is recorded here rather than
  asserted.
