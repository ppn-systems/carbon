## Executive summary

1. **Server tick: two allocators made up 94% of steady-state bytes, and both are fixed (PERF-1, PERF-2).** A closure in `RiverNetwork.Prewarm` was allocated on every loop iteration, cache hits included. The progression blob was re-serialized for every player every 10 ticks. At 8 players the tick drops from **136 to 2 B/tick**. A new test locks in a budget.
2. **The biggest server allocator sat outside the tick.** `WorldOutboundSink.SendEntityDeltaBatch` built 7 arrays per observer per tick: 1,372 B per batch, about **0.66 MB/s at 16 players** (PERF-3, the open part of round-1 HP-1). The packet serializes arrays by `Length`, so exact-length columns are now pooled per entry count (fixed).
3. **Client frame (measured under xvfb with Mesa software GL): 1.4–4 KB allocated per frame, 28–35 draw calls, and 2.2–3.7 ms CPU (p50).** The largest per-frame allocators are the remote-view array rebuilt every frame (PERF-5, ~12% of sampled bytes), HUD number strings (PERF-7), and per-cloud closures (PERF-16, fixed). The window title is also set every frame (PERF-6).
4. **`MultiplayerSession` keeps growing: 3,440 lines in round 1, 4,175 now** (6 partials, 122 fields). `WorldGameplayScene.Update` is a single 474-line method. There was no client size guard; one is added now (GUARD-2).
5. **DDD: invariants live at call sites, not in owners.** There are 17 hand-written mana/stamina writes, 11 `SetHealth` calls, and 3 different damage-mitigation formulas, one of which skips the invulnerability check (DOM-1…DOM-3). Ids are raw `ulong`s, and one value goes by two names (connection id and session id, DOM-6).
6. **Static mutable state on the client.** The terrain bake scratch was process-global (TS-11). It is fixed in this round. Ambient `SyncedFoodCatalog` / `GameText` globals remain (COUP-2). The client now has the same static-state guard as engine and server.

## 1. Performance

### 1.1 Server tick: measured

**Harness:** `tests/server/Carbon.Host.Tests/TickAllocationHarness.cs`. It runs a real `AuthoritativeWorld` on SQLite with a no-op outbound sink, *N* players walking small circles near spawn, and the monsters that populate around them. The table shows 900 warm-up ticks followed by 900 measured ticks, as bytes allocated on the tick thread per `StepFixedTick` and mean wall time per tick. Attribution comes from EventPipe `GCAllocationTick` stacks over 60,000 ticks.

| Players | Before: B/tick | After: B/tick | ms/tick (before → after, noisy shared VM) |
| ---: | ---: | ---: | :--- |
| 1 | 25 | 8 | 0.47 → 0.48 |
| 8 | **136** | **2** | 0.85 → 0.87 |
| 16 | 327 | 59 | 1.13 → 1.09 |
| 32 | 540 | 3 | 1.44 → 1.60 |

Over 60,000 ticks at 16 players, the long-run average is **5 B/tick** after the fix (it was about 274). What remains is warm-up growth (chunk creation, `List` and `Dictionary` resizes) and monster respawns. A respawn allocates a `StatSheet` with a `List<StatModifier>` and a `PathWaypointBuffer` attachment (round-1 ECS-3). The 16-player row is higher because that run happened to land a respawn wave inside the measured window. The PR does not claim a CPU-time change; the deltas are within run-to-run noise.

### 1.2 Server I/O: AoI replication and serialization

| ID | Sev | Finding | Fix |
| :--- | :--- | :--- | :--- |
| PERF-3 | High | `server/Carbon.Host/WorldOutboundSink.cs:91-97` (`SendEntityDeltaBatch`) allocates `ulong[]`, `byte[]` and five `float[]` sized to the entry count, per observer per tick. On top of that comes the async state machine and `Task` of `Dispatch…Async` (15 fire-and-forget dispatch sites). For 16 observers seeing about 40 entities each, that is 29 B × 40 + 7 × 24 B array headers + about 200 B for the `Task`, which comes to ~1.5 KB per observer per tick, or **~0.7 MB/s at 30 Hz** (arithmetic estimate). `EntityDeltaBatch` serializes its arrays by `Length` (`contracts/Carbon.Contracts.Entities/S2C/EntityDeltaBatch.cs:38-63`), so oversized pooled arrays would put garbage on the wire. | **Columns fixed** in `perf/outbound-delta-buffers` (exact-length sets pooled per entry count; the Nalix packet pool turned out not to keep array properties, so per-packet reuse was not viable). Original options: **without a wire change:** keep the column arrays on each pooled packet and reallocate only when `count` changes, which is rare for a stable AoI. Alternatively, keep per-connection exact-length array caches. Replace the fire-and-forget `Task` with a per-connection send channel, which also gives ordering and backpressure (round-1 HP-1). **With a wire change (ADR, protocol bump):** one packed `byte[]` column block plus a count, which can then come from `ArrayPool`. |
| PERF-13 | Medium | Serialize once, send many: every observer gets its own `EntityDeltaBatch` serialization, even when two observers see identical entries. This is inherent to per-observer deltas. Spawn snapshots of the same entity are re-serialized per observer (`AoiReplicator`). | Cache the serialized spawn frame per entity per tick in `AoiReplicator`. Each recipient gets the bytes. |

### 1.4 GPU batching and draw calls

`SpriteBatch` (4,096 quads, one draw per same-texture run) and `GeometryBatch` (16k vertices) are sound, and `GlStateCache` filters redundant binds. There are no raw GL state changes inside per-entity loops.

| ID | Sev | Finding | Fix |
| :--- | :--- | :--- | :--- |
| PERF-8 | High | The HUD is the bulk of the measured 28–35 draws per frame. `CarbonUiSkin` uploads separate Body and Frame textures for 6 styles, 12 in total (`CarbonUiSkin.cs:150-155,398-403`), with `15.png` uploaded 4 times. `DrawPanel` draws Body then Frame (`:299,304`), so every panel breaks the batch twice. The hotbar alone is 20 draws (`HotbarAndItemWidget.cs:51-68`). | PERF-14 | Medium | `DrawOutlinedString` lays out and draws each string 9 times (8 outline offsets + fill, `graphics/.../TextRenderer.cs:131-155`). | PERF-15 | Low | `GeometryBatch` re-uploads the whole VBO and EBO on every flush (`graphics/Carbon.Graphics.Batching/Geometry/GeometryBatch.cs:277-300`). | Upload only `[0, count)` with `BufferSubData`, or orphan the buffer. |
